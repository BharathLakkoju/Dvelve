# Role

You are Claude Code acting as the environment and workflow assistant for Dvelve — responsible for getting the project running locally and keeping day-to-day development consistent.

# Objective

Set up, run, and validate changes to Dvelve's backend and frontend correctly, using the project's actual scripts and dependency files rather than assumptions, and flag any environment issue (missing Ollama, missing system libs, missing env vars) clearly instead of silently working around it.

# Context

- **Two independently run services**, both expected on fixed local ports:
  - Backend (FastAPI): `http://localhost:8000`, started from `backend/` with `uvicorn main:app --port 8000 --reload`.
  - Frontend (React/Vite): `http://localhost:5173`, started from `frontend/` with `npm run dev`.
- `start.bat` starts both at once but hardcodes an author-specific Windows path (`d:\workFiles\ai-automation-web-app\...`); it's a convenience shortcut for the original machine, not a portable script — use the manual two-terminal start above in most cases.
- **Backend dependencies**: `backend/requirements.txt` — key ones are `fastapi`, `uvicorn[standard]`, `asyncpg`, `sse-starlette`, `httpx`, `beautifulsoup4`, `duckduckgo-search`, `chromadb`, `weasyprint`, `markdown`, `python-jose[cryptography]`, `bcrypt`, `slowapi`, `python-dotenv`. Install with `pip install -r requirements.txt` inside a virtualenv.
- **Frontend dependencies**: `frontend/package.json` — React 19, Vite, TypeScript, TailwindCSS v3, Zustand, `react-router-dom`, `react-markdown` + `remark-gfm`, `framer-motion`, `lucide-react`. Install with `npm install`.
- **Environment variables** (backend, via `python-dotenv` / `.env` in `backend/`, not committed — see `.gitignore`):
  - `SECRET_KEY` — JWT signing secret. If unset, the app generates a random one at startup and logs a warning; all existing tokens become invalid on every restart until this is set.
  - `ENABLE_API_DOCS` — set to `true` to re-enable `/docs`, `/redoc`, `/openapi.json` (disabled by default as a hardening measure).
  - `OPENROUTER_API_KEY` — required for **online mode** (the `offline_mode=false` toggle). Get one at https://openrouter.ai/keys. Online mode never falls back to mock data — without this key set, every online research run fails with a clear error instead of silently mocking.
  - `OPENROUTER_MODEL` — optional, defaults to `openrouter/free` (OpenRouter's auto-router alias to a currently-available free-tier model, so the default doesn't rot as specific free model slugs get renamed/retired). Set to a specific model id (e.g. `openai/gpt-4o-mini`) to pin one; paid models will incur OpenRouter usage charges.
  - `DATABASE_URL` — **required**. Postgres connection string for the `users`/`sessions` tables (`backend/services/database.py`); the app raises at startup if it's unset. Use Neon (https://neon.tech) or any Postgres — there is no SQLite fallback anymore, precisely because a local DB file was silently wiped on every restart/redeploy on hosts with an ephemeral filesystem (e.g. Render's free tier). Use the pooled connection string (host contains `-pooler`) to stay within serverless Postgres connection limits.
  - `CHROMA_DB_PATH` — optional, overrides where the ChromaDB vector store lives (`backend/services/vector_store.py`), e.g. `/data/chroma_db`. Defaults to `./chroma_db`. Unlike users/sessions, the vector store is still local disk — on an ephemeral host it resets on restart, which is acceptable since it's a retrieval cache, not source-of-truth data.
- **Persistence created at runtime** (already gitignored, don't commit): `backend/chroma_db/` (ChromaDB vector store, plus a downloaded ONNX embedding model on first live-mode run). Users and sessions live in Postgres (`DATABASE_URL`), not on local disk.
- **Optional system dependency**: PDF export (`/api/sessions/{id}/export/markdown`'s PDF sibling) requires `weasyprint`, which itself needs system-level Cairo/Pango libraries — this can fail on a fresh machine even if `pip install weasyprint` succeeds, since those are OS packages, not Python packages.
- **Tests**: `backend/tests/` (pytest + pytest-asyncio) and `frontend/src/**/*.test.{ts,tsx}` (Vitest + React Testing Library). Backend tests run against the real Neon DB configured via `DATABASE_URL` — there's no separate test database — but every fixture that creates data uses a `pytest-<uuid>`-namespaced email and cleans itself up afterward (see `backend/tests/conftest.py`'s module docstring), so it's safe to run against your dev database. One test module (`test_research_cancellation_live.py`) boots a real `uvicorn` server in a background thread instead of the in-process ASGI test client, because simulating a genuine client disconnect (to test the "Stop Research" cancellation path) isn't possible with `httpx.ASGITransport` — it runs everything in-process with no real transport layer.
  - Backend: `cd backend && pip install -r requirements-dev.txt && python -m pytest tests/ -v`
  - Frontend: `cd frontend && npm test` (or `npm run test:watch` during development)
- **Connecting to Ollama** (used by offline mode for real local generation — offline mode still works with zero setup by falling back to mock data if Ollama isn't running): install Ollama, pull a model (e.g. `ollama pull llama3.2`), then in the app's Settings page point it at `http://localhost:11434`. Offline mode auto-detects whether Ollama is reachable each run — no toggle needed beyond "Offline Mode" itself.
- **Online mode** (`Offline Mode` toggled off) always uses OpenRouter cloud generation plus live DuckDuckGo web search — it requires `OPENROUTER_API_KEY` (see above) and outbound internet access, and does not fall back to mock or to Ollama if that's missing.

# Instructions

- Start the backend and frontend in two separate terminals for normal development (rather than `start.bat`) so you can see each service's logs clearly: `cd backend && uvicorn main:app --port 8000 --reload` and `cd frontend && npm run dev`.
- Before running the backend for the first time, create and activate a Python virtualenv, then `pip install -r backend/requirements.txt`; before running the frontend, `cd frontend && npm install`.
- Create a `backend/.env` (gitignored) with at least `SECRET_KEY=<output of: python -c "import secrets; print(secrets.token_hex(32))">` for any session that needs auth tokens to survive a backend restart, and `DATABASE_URL=<Neon/Postgres connection string>` — the backend will not start without the latter.
- Leave `ENABLE_API_DOCS` unset (or `false`) by default; only set it to `true` in your own local `.env` when you specifically need to browse `/docs` for API exploration, and don't commit that change.
- Test offline-mode behavior (the default, `offline_mode=True`) first for any change to the research pipeline, since it requires no external services; only test live mode afterward, and only if Ollama is actually installed and running.
- Run `cd frontend && npm run lint && npm test` and `cd backend && python -m pytest tests/` before considering a change done; add a test alongside any behavior change (see the "Tests" bullet above).
- Don't commit `backend/chroma_db/`, `backend/.env`, `node_modules/`, or `frontend/dist/` — confirm they're covered by `.gitignore` before adding any new generated-file pattern. (`backend/research_sessions.db` no longer exists — users/sessions moved to Postgres.)
- When a change depends on a system-level package (like Cairo/Pango for `weasyprint`), say so explicitly rather than assuming `pip install` alone is sufficient, and don't silently swallow the resulting error.
- If you can't verify a runtime behavior yourself and there's no test covering it, say so plainly and describe exactly what the user should run and check, rather than asserting it "works."

# Notes

- Ports 5173 (frontend) and 8000 (backend) are hardcoded in multiple places (CORS allowlist in `main.py`, `API_BASE` in `frontend/src/lib/api.ts`, `start.bat`) — if you ever need different ports, update all of them together.
- The CORS allowlist in `main.py` only permits `localhost:5173`, `localhost:3000`, and `127.0.0.1:5173` — running the frontend on a different port or host will silently fail CORS, not error obviously, so check this first if API calls mysteriously don't reach the backend.
- ChromaDB's first live-mode run downloads a small (~30MB) local embedding model, so "fully offline" really means "offline after that one-time download," not "no network ever."
- Rate limiting on `/api/research` is 10 requests/minute per client IP (via `slowapi`); repeated manual testing can trip this limit and look like a bug when it's actually the rate limiter working as intended.

# Deployment

- **Backend on Render** (`render.yaml`, free tier): Render's free plan has no persistent disk option at all. Users/sessions are stored in Neon Postgres (`DATABASE_URL`) precisely to route around that — Postgres persists independently of the container's filesystem, so restarts/redeploys/spin-downs no longer wipe accounts or research history. Set `DATABASE_URL` as a Render secret env var (see `render.yaml`) to the Neon **pooled** connection string. The ChromaDB vector store (`chroma_db/`) still lives on the container's ephemeral disk and does reset on restart — acceptable, since it's a retrieval cache rebuilt from live searches, not the source of truth.
- **Frontend on Vercel**: see `frontend/vercel.json`; set the `VITE_API_BASE` env var in the Vercel project to the deployed backend URL (`frontend/src/lib/api.ts` reads `import.meta.env.VITE_API_BASE`, falling back to `http://localhost:8000` for local dev), and keep `CORS_ORIGINS` on the backend in sync with the deployed frontend origin.
- **Using your local Ollama from the deployed app**: Ollama only ever listens on your machine, so neither the Render backend nor a stranger's browser can reach `http://localhost:11434` on your PC directly. Two separate things make this work:
  - **Settings page "Test Connection"** runs entirely in your browser (see `Settings.tsx`) — it works out of the box against a plain `http://localhost:11434` when you're viewing the app from that same machine. This is a client-side fetch, not a backend proxy, precisely because a cloud-hosted backend testing "localhost" would only ever reach itself.
  - **Actually generating reports with your local Ollama from the deployed backend** requires exposing your Ollama to the internet via a tunnel (e.g. `cloudflared tunnel --url http://localhost:11434`, or `ngrok http 11434`), then setting `OLLAMA_BASE_URL` on Render to that tunnel's HTTPS URL and redeploying/restarting the service. `backend/services/ollama.py` already reads this env var with sane timeouts (3–5s for availability/model checks) — no backend code change is needed, only the env var. Prefer Cloudflare Tunnel's free quick-tunnel or a paid ngrok static domain over ngrok's free tier, since a rotating free ngrok URL means updating `OLLAMA_BASE_URL` on every tunnel restart.
  - Either way, if you want to **test** a tunnel URL from the Settings page (not just use it for generation), the target Ollama instance must also send `Access-Control-Allow-Origin` for your frontend's origin — set `OLLAMA_ORIGINS=https://your-frontend.vercel.app` (comma-separate multiple origins, including `http://localhost:5173` for local dev) before starting `ollama serve`, since Ollama's CORS allowlist defaults to a small set of local origins only. This is unrelated to whether generation itself works — CORS only gates browser fetches, not the backend's own server-to-server calls to Ollama.
  - The backend's `POST /api/ollama/test` endpoint and its SSRF guard (`_validate_ollama_url` in `routers/sessions.py`, localhost-only) are unrelated to this path and were deliberately left untouched — the Settings page no longer calls it, but it stays available as a safe, already-hardened endpoint.
  - **Diagnosing a failed Test Connection**: open the browser DevTools console (F12) when it fails — it distinguishes two very different problems that the UI's generic "Could not connect" message can't tell apart on its own:
    - `ERR_CONNECTION_REFUSED` / `Failed to fetch` with no CORS mention → Ollama isn't running, or the URL/port in Settings is wrong.
    - `blocked by CORS policy` and/or a `403` on `/api/tags` → this is `OLLAMA_ORIGINS` rejecting the site's origin. Ollama does its own origin check independent of standard CORS (returns 403, added to prevent DNS-rebinding attacks), so this happens even for a same-machine `localhost` origin if it's not explicitly allowlisted. The Settings page itself now shows this exact troubleshooting text (with the correct origin value pre-filled and a copy-pasteable command) once a test fails, so most users won't need this doc — but the underlying fix is: set `OLLAMA_ORIGINS`, then **fully quit Ollama from its system tray icon** (closing just the window leaves the background process running with the old env var) and relaunch it.
      - Windows (persistent): `[System.Environment]::SetEnvironmentVariable('OLLAMA_ORIGINS', 'http://localhost:5173,https://your-frontend.vercel.app', 'User')` in PowerShell, then restart Ollama.
      - macOS: `launchctl setenv OLLAMA_ORIGINS "http://localhost:5173,https://your-frontend.vercel.app"`, then restart Ollama.
      - Linux / manual `ollama serve`: `OLLAMA_ORIGINS="http://localhost:5173,https://your-frontend.vercel.app" ollama serve`.
